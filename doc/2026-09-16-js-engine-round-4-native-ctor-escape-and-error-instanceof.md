# JS Engine Round 4 — More Try/Catch Escape Sites, Plus `instanceof TypeError` Was Always False

**Date:** 2026-09-16
**Session:** Follow-up prompted by a direct question ("test malformed URLs and relative resolution") about the previous day's `URL`/`URLSearchParams` work. Testing malformed input immediately surfaced that `new URL('not a url')` crashed the *entire script*, not just the one `try` block around it — the same try/catch-escape bug class from two days earlier, at call sites that investigation hadn't reached.
**Status:** Completed

---

## Summary
Asked to verify malformed-URL handling and relative-URL resolution, which surfaced a real regression-shaped gap immediately: `new URL('garbage')` escaped every `try`/`catch` in the script, aborting everything after it — exactly the try/catch-escape bug fixed two days earlier, but at three native-constructor call sites (`new X(...)` and `X(...)` for any "plain callable JSObject" constructor — `URL`, `URLSearchParams`, `FormData`, `TextEncoder`, `TextDecoder`, and regex-literal construction) that round hadn't reached. Fixing that surfaced a second, separate, and arguably higher-impact bug once errors became reliably catchable: `e instanceof TypeError` (and `instanceof Error`, `instanceof SyntaxError`, etc.) was `false` for *every* error in the engine, including ones built via a script's own `new TypeError(...)` — the built-in Error family had no discoverable `.prototype` at all, the same "callable object built via `createNativeFunction` has no `.properties` map" shape as the pre-fix `Number`/`Array` globals from the first round. Fixed both; folded into three new checks in the existing `language-features` sweep case — 83/83 checks green. Full suite: zero regressions.

## Root Causes

1. **Three native-constructor dispatch sites called a JSObject's own `.nativeFn` completely unwrapped — no try/catch, no JSError conversion.** `evalNew`'s "callable JSObject with nativeFn" branch (used for `new URL(...)`, `new Promise(...)`, and every other constructor built with the `createObject(null)` + `.callable`/`.nativeFn` pattern established across this session — `URL`, `URLSearchParams`, `FormData`, `TextEncoder`, `TextDecoder`), `evalCall`'s equivalent for calling the same shape *without* `new`, and `evalLiteral`'s regex-literal construction (`/pattern/flags` routes through `RegExp`'s own `nativeFn`) all called `obj.nativeFn!(...)` directly. Since these wrapped constructors genuinely throw real native errors on bad input (`new URL('garbage')` really does throw from the underlying native URL parser; `/[unclosed/` really does throw a native `SyntaxError` from the underlying native `RegExp`), any such throw propagated as a real, unwrapped TypeScript exception — bypassing the `JSError`/`ThrowSignal` machinery entirely and aborting the rest of the script, not just the one `try` block around the offending call. This is the identical bug class fixed at four *other* call sites two days earlier; that investigation's probe scripts happened not to exercise a constructor built with this specific object shape that also throws on bad input, so these three sites went unnoticed until a direct "test malformed input" ask reached them. Extracted the fix into one shared `callNativeSafe()` helper (rather than a third copy of the inline try/catch pattern) specifically so a future native-callable dispatch site can't reintroduce the same gap silently, and used it at all three.

2. **`e instanceof TypeError` — and `instanceof` any other built-in Error subtype, or plain `Error` — was `false` unconditionally, for every error in the engine, including ones a script builds itself.** `instanceofCheck`'s prototype-chain walk needs a real `.prototype` object to walk toward; the `Error`/`TypeError`/`RangeError`/`ReferenceError`/`SyntaxError` globals were each built via `createNativeFunction`, which returns a bare `{type:'closure', ..., nativeFn}` shape with **no `.properties` map at all** — the exact same shape gap this session's first round had already found and fixed for the pre-fix `Number` and `Array` globals (missing static methods because there was nowhere to put them), just manifesting here as a missing `.prototype` instead of missing static methods. Every constructed error — from a script's own `new TypeError(...)`, from `jsError()`, from the native-exception-wrapping added throughout this session — had `prototype: null`, so `instanceofCheck`'s walk found nothing to match against `TypeError.prototype`, immediately failing. Rebuilt the whole Error family with the same "plain callable JSObject with a real `.properties` map" pattern already used for `URL`/`Array`/`Number`, with a correct inheritance chain (`TypeError.prototype.prototype === Error.prototype`, matching real JS, so `instanceof Error` is also true for a `TypeError` instance) and each prototype registered in a small shared registry (`registerErrorPrototype`/`makeErrorObject`, in `values.ts`) that every internal error-construction site (`jsError()`, both `callJSFunction`'s and `callFunction`'s native-exception-wrapping catch blocks) now goes through instead of building an unlinked `createObject(null)` error by hand. Also added `Error.prototype.toString()` (`"Name: message"`) and two previously-missing standard subtypes, `EvalError`/`URIError`, while rebuilding this family.
   - **Known, deliberate limitation of the fix:** the prototype registry is one shared, module-level map, not scoped per page/tab — with multiple tabs open, the most-recently-loaded page's Error prototypes are what an *internally-thrown* error (not a script's own `new TypeError()`, which is unaffected either way) links against. Flagged in-code (`ponytail:` comment) rather than fixed, since properly scoping it per-`Interpreter` is a materially larger change and the mismatch only matters for a fairly narrow combination (multiple tabs open, an engine-internal throw, and a script checking `instanceof` against its own tab's specific constructor).

## Notes
- This round is a direct continuation of the try/catch-escape bug from two days earlier, not a new bug class — a useful reminder that "fixed the call sites the investigation happened to reach" and "fixed every call site" are different claims, and a shared helper (`callNativeSafe`, mirroring the equally-shared `jsError`/`makeErrorObject`) is worth the small extra indirection specifically to make the *next* missed site less likely, not just to deduplicate the current ones.
- The `instanceof TypeError` bug was invisible until root cause 1 was fixed — with native throws escaping every `try`/`catch`, no script's `catch (e) { if (e instanceof TypeError) ... }` handler ever got a chance to run at all, so the separate, underlying `instanceof` bug had no opportunity to manifest as a wrong answer instead of just... never being reached. This mirrors the exact same layering pattern noted in the two earlier rounds this session (fixing one foundational bug turns a *different* bug's symptom from "nothing happens" into "the wrong thing happens," which is what makes it findable at all).
- Verified relative URL resolution (absolute-path, sibling-path, `../` parent-relative, query-only, protocol-relative, and absolute-URL-overrides-base) all resolve correctly — this comes for free from wrapping the real native `URL` parser (established in the previous day's work) rather than needing any new resolution logic; the only gap was that a *failed* resolution (bad base, or a relative string with no base at all) couldn't be caught before this round's fix.

## Verification Steps
1. Asked to specifically test malformed URLs and relative resolution; wrote a probe covering both through the standalone `runJS()` harness established earlier in the week — the very first malformed-URL case aborted the whole script with no console output at all, immediately flagging the try/catch-escape pattern rather than a URL-parsing-logic bug.
2. Traced the exact dispatch path (`evalNew`'s "callable JSObject" branch) and found two sibling call sites with the identical unwrapped-`nativeFn`-call shape by grepping for the same pattern rather than assuming only one site was affected.
3. Fixed with one shared helper, re-verified the original malformed-URL probe, then additionally verified relative resolution (path, `../`, protocol-relative, absolute-overrides-base) and a malformed regex literal — confirming the fix generalized rather than just patching the one reported case.
4. Adding checks to the permanent e2e sweep surfaced the `instanceof` bug specifically: `e instanceof TypeError` came back `false` in the *real* Electron app even though the standalone harness probe (which only checked `.name`/`.message`) had looked clean — a reminder that a probe only tests what it asserts.
5. Root-caused via `instanceofCheck`'s prototype-walk requirements, confirmed via a direct probe that manually-constructed errors (`new TypeError(...)`) had the same bug, not just internally-thrown ones — ruling out a narrower "only engine-thrown errors are unlinked" theory before implementing the broader fix.
6. Ran the full `npx vitest run` (0 regressions) and the complete Electron e2e suite (5/5 specs, 83/83 sweep checks) after rebuilding the web bundle.
7. Deleted all scratch investigation files before this final verification pass.
