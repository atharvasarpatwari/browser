# JS Engine Round 5 — The Classic Prototype-Inheritance Pattern Was Completely Broken (and So Was Every Template Literal Escape)

**Date:** 2026-09-16
**Session:** Open-ended continuation ("keep going, find more real gaps to fix") of the same JS-engine bug hunt as the previous four rounds this week. Started from `for-in` semantics and control-flow probes, then followed one bug into the next: fixing `for-in` surfaced a class-member-enumerability deviation, which led to probing the pre-ES6 `function Ctor(){}` + `.prototype` inheritance idiom, which turned out to be fundamentally non-functional in several compounding ways, which led to discovering `Function.prototype.call/apply/bind`, `Object.prototype`'s base methods, and `Object.getPrototypeOf` were all entirely unimplemented, and finally that template literals never decoded escape sequences at all.
**Status:** Completed

---

## Summary
`for-in` was listing every property on an object regardless of its `enumerable` flag — real-world impact: `for (var k in someArray)` leaked all ~30 built-in array method names alongside the actual numeric indices. Fixing that led straight into the classic `function Ctor() {}; Ctor.prototype.method = ...; new Ctor()` inheritance pattern — extremely common in real-world/legacy JavaScript — which was **completely non-functional**: `new Ctor()` never linked the new instance to `Ctor.prototype` at all, so every inherited property and method read back `undefined` and `instanceof` was always `false`. Chasing the fix through the object model surfaced that plain function objects had **no `.properties` map whatsoever** (a structural gap distinct from, but the same shape as, three earlier rounds' "closure objects can't hold static state" bugs) — which in turn meant `Function.prototype.call/apply/bind` were entirely unimplemented (`Parent.call(this, ...)`, the backbone of the inheritance pattern, silently evaluated to `undefined` without ever invoking `Parent`), `Object.prototype`'s base methods (`hasOwnProperty`, `isPrototypeOf`, `toString`, `valueOf`, ...) were absent from every object/array/class instance, and `Object.getPrototypeOf`/`setPrototypeOf` didn't exist. Along the way, testing `String.raw` surfaced the single biggest surprise of the round: **template literals never decoded escape sequences at all** — `` `a\nb` `` produced the 4-character string `a\nb` (literal backslash) instead of a 3-character string with a real newline, for every template literal in the engine, tagged or not, ever. Fixed all of it at the root; folded into a new 10-check `prototype-and-function-methods` sweep case (93/93 checks green). Full suite: zero regressions.

## Root Causes

1. **`for-in` listed every property regardless of its `enumerable` flag, and never walked the prototype chain for inherited enumerable properties.** `execForIn` read `[...obj.properties.keys()]` unconditionally — every non-enumerable built-in method (attached directly to each array/Map/Set/... instance's own `.properties`) leaked into the loop alongside real data properties: `for (var k in [1,2,3])` produced `"0","1","2"` followed by `"length","push","pop","join",...` (the full `arrayNativeMethods` table). Rewrote it to visit own enumerable string keys first (skipping `@@symbol:`-prefixed keys), then walk the prototype chain for inherited enumerable keys not already seen at any earlier level — an own property, even non-enumerable, correctly shadows a same-named inherited one, matching real `for-in` semantics. This also surfaced that `buildClassObject` marked every class method/accessor `enumerable: true` (harmless before this fix, since nothing checked the flag; a real spec deviation now that `for-in` respects it, since real class members are non-enumerable) — corrected to `false`.

2. **The classic `function Ctor() {}; Ctor.prototype.method = ...; new Ctor()` inheritance pattern was completely broken: `evalNew` never linked a new instance to its constructor's `.prototype`.** The "Function constructor (JSFunction closure)" branch always built the new instance as a bare, unlinked `createObject(null)` — so every inherited property and method read back `undefined`, and `instance instanceof Ctor` was always `false`, for every plain (non-class) constructor function in the engine. Fixed by looking up `Ctor`'s own `.prototype` (via the existing lazy `getPropertyValue` machinery) and linking the new instance to it, matching real `[[Prototype]]` semantics on construction. A second, compounding bug in the same area: `instanceofCheck` still returned `false` afterward, because it only checked `rightObj.properties?.get('prototype')` — and, per root cause 3, a plain function had no `.properties` map at all, so this lookup always failed regardless of the real link. Fixed with a fallback to the same lazily-cached prototype object `evalNew` now reliably populates.

3. **Plain function objects (`JSFunction`) had no `.properties` map at all — a structural gap, not a bug in any one place.** `JSObject` has always carried `properties: Map<string, PropertyDescriptor>`; `JSFunction` (returned by `createFunction`/`createNativeFunction` for every ordinary function, arrow function, and native builtin in the engine) never did. This one gap was the root cause behind several distinct, independently-observed breakages: assigning to `Ctor.prototype = Object.create(...)` (the standard sub-classing idiom) or any other static property on a function crashed the *entire script* with `Cannot read properties of undefined (reading 'set')` — an unwrapped native exception escaping every `try`/`catch`, the same bug class fixed at other call sites in Rounds 1 and 4; `findPropertyDescriptor`'s prototype-chain walk crashed the same way (`reading 'get'`) whenever the walk reached a plain function object; and it made `Function.prototype.call/apply/bind` and any Object.prototype fallback (root causes 4–5) structurally impossible to implement via the existing property-lookup machinery. Fixed at the root: added a real `properties: Map` field to the `JSFunction` interface, populated by both factory functions (`createFunction`, `createNativeFunction`) and the three other ad hoc `type: 'closure'` object-literal sites in the codebase (`custom-elements.ts`, `gc.ts` ×2, a class-constructor placeholder in `interpreter.ts`), so every function object in the engine now has one, unconditionally, from creation.

4. **`Function.prototype.call`, `.apply`, and `.bind` were entirely unimplemented.** With no properties map to hang them on (root cause 3), a function's `.call`/`.apply`/`.bind` property access fell through to a plain `undefined` — so `Animal.call(this, name)`, the mechanism the classic inheritance pattern uses to run a parent constructor against a subclass's `this`, silently evaluated to `undefined` *without ever invoking `Animal` at all*, rather than throwing or doing anything visibly wrong. Implemented all three as a lazily-constructed native-function wrapper around the target closure, using the interpreter's existing `callFunction` primitive (already used for getter/setter invocation) to actually run the target with the requested `this` and arguments. `.bind` additionally tags its returned function with the original target and preset args so `evalNew` can unwrap back to it — a bound function is still constructible in real JS (`new (fn.bind(x))()`), ignoring the bound `this` but keeping the preset args, which a naive "just call the bound wrapper" `new` dispatch would have gotten wrong (silently discarding the bound `this` and returning an unlinked, empty instance instead of ever constructing the real target).

5. **`Object.prototype`'s base methods — `hasOwnProperty`, `isPrototypeOf`, `propertyIsEnumerable`, `toString`, `valueOf`, `toLocaleString` — were completely absent from every plain object, array, and class instance.** Every object's prototype chain terminates in a null-prototyped object built by `createObject(null)`, never a real `Object.prototype`, and no property-lookup path had a fallback for these standard methods. `obj.hasOwnProperty(k)` — an extremely common idiom, notably for guarding a `for-in` loop against inherited properties — silently evaluated to `undefined` (not a crash, since calling a non-function callee is itself a no-op in this engine, but silently wrong) instead of ever running. Added a shared fallback consulted only after both the own-property and full prototype-chain lookups come up empty, so it never shadows a real user-defined override of any of these names.

6. **`Object.getPrototypeOf`/`setPrototypeOf` didn't exist.** Neither was registered on the `Object` global at all. Added both, using the `[[Prototype]]` link's own internal field directly (`obj.prototype`) rather than re-deriving it, since `createObject`/`evalNew` already set that field correctly once root cause 2 was fixed.

7. **`String.fromCharCode`, `.fromCodePoint`, and `.raw` were entirely absent as static methods.** `String` was a bare `createNativeFunction` with nothing attached — so `` String.raw`a\nb` `` threw `"tag is not a function"` for every tagged-template use of `String.raw`, a real (if less common than `.call`/`.apply`) pattern. Added all three; `.raw` walks the tag-call convention's `.raw` array (per root cause 8) and concatenates it with the substitution values per spec.

8. **Template literals never decoded escape sequences at all — the biggest surprise of the round.** `` `line1\nline2` `` produced a 12-character string with a literal backslash and `n`, not an 11-character string with a real newline; `\t`, `\\`, `` \` ``, `\${`, `\u`, `\x`, and every other string escape were equally unprocessed, for *every* template literal in the engine, tagged or not, since it was created. The lexer's template scanners (`readTemplate`/`scanTemplatePart`) took a raw source slice as the token's value and only ever skipped past an escaped character to avoid mis-detecting a terminator — they never decoded it. This also meant the previously-documented `String.raw`-reuses-cooked-text simplification (a deliberate, flagged shortcut from an earlier round, back when `.raw` didn't need to differ from a broken `.value` to look "correct") was masking this far larger bug: since neither raw nor cooked was ever decoded, tagged and untagged template literals looked consistent with each other while both being wrong. Fixed by teaching the lexer to decode escapes into a real cooked value (sharing the exact decode logic `readString` already used for ordinary string literals, factored into one `decodeEscape()` helper) while separately preserving the untouched source slice as a new `raw` field threaded through `Token` → `AST.TemplateElement` → `evalTaggedTemplate`'s `.raw` array — so cooked and raw template text are now genuinely distinct, matching spec, instead of coincidentally identical-and-wrong.

## Notes
- Root causes 2–7 all trace back to the same single missing field (`JSFunction.properties`) either directly or in how they were investigated — a useful reminder that a "shape gap" bug (an object missing a field other code assumes exists) rarely has just one symptom; the other four call sites were found by asking "what else would this same missing map break?" rather than stopping at the first crash.
- The template-literal escape bug (root cause 8) was found by chasing what looked like an unrelated, narrower complaint (`String.raw` throwing "not a function") — implementing `String.raw` and testing it against a real tagged template immediately showed the output was wrong in a way `String.raw`'s own absence couldn't explain, which is what led to checking plain untagged template literals and finding they were equally broken.
- Consistent with Rounds 1 and 4's "try/catch escape" bug class: both the `evalAssignment` crash (root cause 3) and the pre-fix `findPropertyDescriptor` crash were raw, unwrapped TypeScript exceptions that aborted an entire script past every sandboxed `try`/`catch`, not just symptom-level wrong answers — worth specifically checking for on every new crash found this way, since it means a single bug can look far scarier (and far more like several unrelated ones) than it is until root-caused.
