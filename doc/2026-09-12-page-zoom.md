# Page Zoom — Wiring the Orphaned ZoomManager to Real Rendering

**Date:** 2026-09-12
**Session:** Continue improving the browser after the DevTools suite (Console/Elements/Network) — fix zoom, which was clickable but did nothing to the actual page.
**Status:** Completed

---

## Summary
The status bar's `−`/`%`/`+` zoom control was already fully rendered and clickable, and a complete, independently-tested `ZoomManager` (`src/browser/navigation-controls/zoom.ts`, clamped 25–300% in 10% steps) already existed — but nothing connected the two, and nothing applied any zoom to the rendered page. Clicking `+`/`−` silently did nothing: the click handler computed a new percentage and handed it to `StatusBar.setZoom()`, which only stored the number on a model object that was never re-rendered, and `ZoomManager` itself was never instantiated anywhere outside its own test file. This was the same "real, tested capability with no wire to the running app" shape as the DevTools panels built earlier today.

## Root Causes
1. **`ZoomManager` was never instantiated.** `grep -rn "new ZoomManager" src` outside its own file/tests returned nothing — a fully clamped, event-emitting zoom model existed and was completely inert.
2. **The status bar view's own zoom buttons duplicated (and diverged from) `ZoomManager`'s logic instead of using it** — hardcoded `current > 50` / `current < 200` guards and `±10` arithmetic directly in the click handlers, rather than delegating to the real zoom model's 25–300 bounds.
3. **`StatusBarView.update()` was never called for the status bar at all.** Even the cosmetic percentage label was stale after the very first click — `StatusBar.setZoom()` updated the model's `_zoom` field, but nothing ever pushed that back into the DOM (`browser-window.ts` calls `.update()` for the toolbar, bookmark bar, tab strip, and address bar, but never for the status bar).
4. **Nothing applied zoom to the actual rendered page.** No code path anywhere calls `webContents.setZoomFactor`/`setZoomLevel`, and there was no equivalent for Nova's own canvas-rendered page content either — the feature had no rendering effect at any layer.

## Notes
- Zoom is applied as a CSS `transform: scale(factor)` (`transform-origin: top left`) on the rendered `<canvas>`/iframe element in `content-renderer.ts`, not by re-running layout at a different viewport size. This is a visual/optical zoom (like early browsers, or a quick pinch-zoom), not the reflow-based zoom modern browsers do — chosen because it's a small, safe change confined to the UI layer, versus threading a zoom factor through the layout engine's viewport math (a materially bigger, riskier change). `.content-area`'s existing `overflow:auto` (`desktop-layout.ts`) means Chromium's scrollable-overflow calculation (which accounts for transformed children) makes the zoomed-in content scrollable without any extra work.
- Deliberately did **not** add `Ctrl+`/`Ctrl-` keyboard shortcuts for this. Electron's default `viewMenu` role already binds those to its own native `zoomIn`/`zoomOut`/`resetZoom` (applied to the whole `webContents`, chrome included) — the exact same collision shape as the F12/DevTools shortcut fixed earlier today. Adding a second, page-level binding on the same keys would either double-zoom or produce confusing, inconsistent behavior. The status bar buttons are the only zoom entry point for now.
- Because `BrowserEngine` has one shared rendering pipeline for the whole app (see the Network tab changelog from earlier today), this is necessarily a single, app-wide zoom level rather than a genuinely per-tab one — consistent with how tabs don't currently hold independent live state at all.
- `StatusBarView.update()` is now called explicitly from the `ZoomManager` event handler rather than fixing whatever broader gap causes the status bar to never receive `.update()` calls elsewhere (blocked count, hover URL, etc. have the same staleness risk) — that's a separate, wider issue left alone here to keep this fix scoped to zoom.

## Files Modified
| File | Change |
|------|--------|
| `src/ui/pages/browser-window.ts` | Instantiates `ZoomManager`; `zoomChanged` now calls `zoomManager.setZoom()` instead of poking the status bar model directly; `ZoomManager`'s `onEvent` pushes the new zoom into `statusBar.setZoom()` + `statusBarView.update()` + `contentRenderer.setZoom()` |
| `src/ui/components/status-bar/status-bar.view.ts` | Removed the hardcoded 50/200 pre-checks on the zoom buttons — `ZoomManager`'s own 25–300 clamp is now the single source of truth |
| `src/ui/components/content-renderer/content-renderer.ts` | Added `setZoom(factor)`, applying/reapplying a CSS transform to the canvas on every render (including a fresh canvas after navigation) |
