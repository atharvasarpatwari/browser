# CSS Engine Round 3 — Transforms Were Completely Non-Functional, Plus Three More Real Gaps

**Date:** 2026-09-14
**Session:** Direct continuation of `2026-09-14-css-engine-round-2-more-real-gaps.md`. Continued the same sweep methodology into a third, disjoint set of real-world CSS features (transforms, multi-layer backgrounds, mixed-unit `calc()`, grid item self-alignment, flex/grid container paint order, multi-argument `:not()`).
**Status:** Completed

---

## Summary
Four more real, independent engine bugs, the first of which is the most severe found across all three rounds: **CSS `transform` had no visual effect whatsoever**, for any element, animated or not. All 6 new fixtures / 13 checks pass; the full unit and e2e suites stay green. One additional fixture (`:not()` with multiple arguments) was written to confirm round 1's comma-splitting fix also holds for negation, not just `:is()`/`:where()` — it did, no bug found there.

## Root Causes
1. **`transform` did nothing at all — not for static values, and only partially for animated ones.** The stacking-context builder (`stacking.ts`'s `createContext()`) only ever read a transform from an *animation overlay resolver* — a plain `transform: translate(...)` set via CSS with no animation running was never even looked at, since `options?.transformResolver?.(el)` returning `undefined` short-circuited the whole branch with no fallback to the computed style. Fixing that exposed a second, deeper bug: even when a transform *did* reach the pipeline, the software rasterizer's `translateX`/`translateY` state fields — already declared, already correctly saved/restored across `save()`/`restore()` — had no `case 'translate'` to ever write them, and no drawing primitive (`fillRect`, `fillText`, `drawImage`, `clip`, gradients, shadows, filters, masks) ever read them. So the *entire* translate pipeline was inert scaffolding; nothing using `transform: translate(...)` has ever visibly moved in this engine. Fixed by (a) falling back to the computed `transform` style when no animation is overriding it, in both the stacking-context builder and the legacy flat paint-layer path, and (b) adding the missing `case 'translate'` plus a centralized coordinate-offset table applied to every position-bearing paint command, in both the software rasterizer and the GPU rasterizer's command-encoding path. `rotate()`/`scale()`/`skew()` remain unimplemented — see Notes.
2. **Comma-separated `background-image` layers collapsed to one.** `background-image: linear-gradient(a), linear-gradient(b)` was read and parsed as a single string; only whichever gradient the parser happened to produce from the whole un-split value ever painted — every additional layer was silently dropped. (A separate, apparently-unused `enhanced-backgrounds.ts` module already modeled multi-layer backgrounds but was never wired into the live paint path, and had its own bugs — a naive `.split(',')` that would itself mis-split a single gradient's internal commas, and forward instead of reverse paint order — so it wasn't reused as-is.) Fixed by splitting `background-image` (and `background-size`/`background-position`, cycling shorter lists per spec) on *top-level* commas only, and painting layers back-to-front so the first-listed layer ends up on top, per spec.
3. **`calc()`/`min()`/`max()`/`clamp()` mixing a percentage with another unit resolved to a silently wrong value, not just "unresolved".** `calc(100% - 20px)` collapsed a 200px-wide box's child to 80px instead of 180px. The math-function module's own doc comment already stated the intended design — mixed-unit expressions should be "preserved as-is for the layout engine to resolve" — and the percentage converter correctly returned `null` (unresolvable) in isolation. But `DEFAULT_MATH_CTX` carried a leftover `percentageBasis: 100` that nothing had ever actually consulted before now, and merging it into every caller's context via `{...DEFAULT_MATH_CTX, ...context}` meant the percentage converter's own `undefined` check could never fire — so the cascade's *early*, layout-unaware computed-value resolution pass silently resolved `100%` against the placeholder `100` instead of leaving it for layout, baking in a wrong pixel value before layout ever ran with the real containing-block width. Fixed by removing the bogus default (restoring the documented "leave unresolved until a real basis is known" behavior for callers that don't have one) and adding the one thing that actually was missing: `layout-engine.ts`'s `resolveLength()`, which already receives the true containing-block width, now finishes the resolution the cascade stage correctly declined to do.
4. **`display:flex`/`display:grid` containers with their own background or border painted over their own children.** `classifyDisplay()` correctly separates `'flex'`/`'grid'` from `'block'` because layout needs a different formatting-context algorithm for each — but the *stacking/paint-order* classifier (`classifyElementIntoLayer()`) reused that exact same distinction to decide which paint layer an element belongs to, and anything that wasn't literally `'block'` fell into the inline-level bucket (CSS2.2 Appendix E "Level 4"), which paints *after* plain block-level content ("Level 2") — where the container's own non-positioned children had already landed. So a block-level flex/grid container's own background painted last, on top, hiding every child underneath it whenever the container had a visible background/border. This had gone unnoticed because none of the flexbox/grid fixtures from rounds 1–2 happened to put a background on the *container* itself. Fixed by treating block-level `'grid'`/`'flex'` (not `'inline-grid'`/`'inline-flex'`) the same as `'block'` for stacking purposes, matching how a real browser treats them.

## Notes
- Root cause #1 is scoped to `translate()` only. `rotate()`/`scale()`/`skew()` remain **unimplemented** — actually rotating or scaling painted pixels needs real affine-transform rendering in the rasterizer (remapping a whole rectangle of pixels through a matrix, not just offsetting a paint position), a materially larger feature than restoring a completely-dead translate path. Confirmed this doesn't regress anything: `isPureTranslation4x4()` already correctly identified non-translation matrices and returned `null`/no-op for them before this fix, and still does.
- Root cause #4's impact was likely invisible in most real testing because the most common failure mode — a colored card/panel built with `display:flex` or `display:grid` and a background — needs the container to have a *visible* background to notice anything wrong; a transparent-background flex/grid container (the shape of every flexbox/grid fixture written in rounds 1–2) never triggers it, since painting "nothing" twice in the wrong order still looks like nothing.
- `enhanced-backgrounds.ts` (the unused multi-layer background module referenced in root cause #2) was left as dead code rather than deleted or wired up — it doesn't match the live command-based paint architecture closely enough to be a clean drop-in, and deleting unrelated dead code was out of scope for this pass.

## Verification Steps
1. Investigated the "which real-world feature areas haven't been swept yet" question by reading the relevant source before writing any fixture, rather than guessing blind — this is what surfaced root cause #1 before a single pixel check ran: reading `paint-engine.ts`'s transform handling showed the *only* code path that ever read a `transform` value was gated behind an animation resolver, with no fallback for the (overwhelmingly common) static case.
2. For each fix, reproduced with a standalone Node repro via `tsx` (`HtmlParser → DomTree → CssParser → computeComputedStyles → LayoutEngine → PaintEngine`, dumping either the computed value, the layout box, the raw paint command sequence, or the rasterized pixel buffer directly) before writing any code change, then re-ran the same repro after the fix to confirm the exact mechanism, not just the symptom.
3. Root cause #3 needed a second pass: the first fix (wiring `percentageBasis` into the `%` converter) didn't fix the live bug, because a *different*, earlier caller (the cascade's computed-value resolver) was already mis-resolving the same expression against a bogus default before layout ever ran. Traced this by comparing the computed style value with what layout actually received, found the value was already wrong before layout, and worked backward to the leftover default.
4. Root cause #4 needed the same treatment: the layout box for the grid item was already exactly correct (confirmed by direct box inspection), so the bug had to be downstream in paint — dumping the actual paint command sequence showed the child's `fillRect` before the parent's, immediately pointing at stacking/paint-order classification rather than layout.
5. Rebuilt the web bundle and reran the full sweep after each fix, confirming each specific check flipped from FAIL to PASS.
6. Ran the full unit suite and full Electron e2e suite (smoke + fidelity-audit + the merged sweep) after all fixes — all green.
