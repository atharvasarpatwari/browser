# JS Engine Round 3 — Classes Were Fundamentally Broken: instanceof, Setters, Fields, and a Stack Overflow

**Date:** 2026-09-15
**Session:** Third round of the same day's bug hunt, moving from language/API gaps into class features specifically, using the same probe-script-through-`runJS()` methodology as rounds 1 and 2.
**Status:** Completed

---

## Summary
A broad class-features probe (basic methods, inheritance, static members, private fields, computed keys, `toString`/`valueOf` coercion) failed almost across the board on the first run — `instanceof` was false for every user-defined class, a class's own setter never fired, static fields didn't even parse, private fields silently mis-parsed into garbage, and a 3-level inheritance chain crashed with a real stack overflow. None of this is exotic: basic OOP with more than one related class is about as ordinary as JavaScript gets. Root-caused and fixed nine distinct issues, the worst being that every method in the file shared one mutable environment for its `super` binding — so defining a second class in the same scope silently rewired what `super` meant inside the first one's methods, and in the right shape that rewiring becomes an infinite loop. Folded into a new `class-features` case (15 checks) in `tests/e2e/js-dom-api-sweep.spec.ts` — 80/80 checks green across all four cases. Full suite: zero regressions (two pre-existing typed-array tests were asserting spec-incorrect behavior that this round's own coercion fix exposed and corrected).

## Root Causes

1. **`static x = 1` failed to parse at all.** `parseClassBody`'s `static` branch always assumed a method followed (`this.expect(TokenType.LParen)` unconditionally right after the key), unlike the non-static branch three lines below it, which already checked `if (this.is(TokenType.LParen))` before deciding between a method and a field. Made the static branch symmetric with the non-static one.

2. **Class fields — both instance (`x = 1`) and the just-fixed static (`static x = 1`) — parsed fine but were then silently discarded.** `buildClassObject`'s member loop only ever matched `MethodDefinition`; a `PropertyDefinition` (what a field parses to) fell through the `if` with no `else` branch and simply vanished. `AST.PropertyDefinition` also had no `static` field at all, so there was no way to even represent which kind a given field was. Added a `static?: boolean` to the AST type, and real handling in `buildClassObject`: a static field evaluates its initializer immediately (with `this` bound to the class object itself) and becomes a real property on the class; an instance field's initializer is deferred and stored (`__instanceFields`, a new field on the class's `JSObjectWithMeta`) for `evalNew` to run per-instance, with `this` bound to the new instance, right after the instance is created — since an initializer can reference `this` (`y = this.x * 2`) or, via `super()`, an inherited base-class field.

3. **`instanceof` returned `false` for every user-defined class, unconditionally.** `instanceofCheck`'s "is this a valid constructor" test (`'closure' in right || (rightObj.type === 'function' && rightObj.callable)`) only recognized closures and plain callable objects — a class is neither; it's its own `type: 'class'` shape. Every `x instanceof MyClass` — including every subclass relationship — short-circuited to `false` before even reaching the prototype-chain walk. Separately, even once recognized, a class's own `.prototype` (the property script code reads as `MyClass.prototype`) is never placed in its `.properties` map — only its *structural* prototype-chain link is — so the existing lookup (`rightObj.properties?.get('prototype')?.value`) would have found nothing anyway. Fixed both: classes are now recognized as constructor-like, and use the structural link directly instead of the empty property lookup.

4. **Assignment (`=`, compound `+=`-style operators, and `++`/`--`) only ever checked an object's own properties for an existing getter/setter — never the prototype chain.** Every non-static class accessor (`get`/`set` methods) lives on the class's shared prototype, not on each instance; assigning to `obj.x = v` when `x`'s setter is inherited found nothing on the instance itself and fell back to silently creating a same-named plain value property that shadows the accessor, so the setter's own logic (and anything it was supposed to keep in sync) never ran. The read side already walked the prototype chain correctly in `getPropertyValue`/`evalMember`; the three write-adjacent paths didn't. Added a shared `findPropertyDescriptor()` helper (walks the chain, used by all three) and fixed the compound-assignment path's *read* of the current value too — it had the identical bug in reverse: an inherited getter-only descriptor was read via its (always-`undefined`) plain `.value` instead of calling `.getter`, so `obj.n += 5` silently computed `NaN` instead of reading `n` correctly first.

5. **A computed class member key (`[expr]() {}`, `static [expr] = 1`) evaluated to the *variable's own name* instead of its value.** `parseClassBody` never tracked whether a key was written with brackets at all — every `MethodDefinition`/`PropertyDefinition` it built had `computed` hardcoded to `false`, and the class-building code's own `String(method.key)` (for the *other* half of this bug) stringified the raw AST node object rather than evaluating it — so `[methodName]() {}` always defined a method literally named `"methodName"`, never whatever the variable held. Fixed by tracking `computed` the same way the object-literal parser already does (checking the token right before the key for a closing `]`), and evaluating the key expression (via the existing `toPropertyKey()`) whenever it's computed.

6. **The most severe bug: every method's closure was the same, shared, mutable enclosing-scope environment — so a second class declared in that scope could silently rewrite what `super` meant inside the first class's already-built methods, up to and including causing a real stack overflow.** `super`/`__superCtor` were bound with `fn.closure.setLocal(...)` *after* `createFunction` had already been given the plain outer `env` as that method's closure — and since every class in the same scope (an ordinary top-level script, e.g. three related classes in one file) was built against that identical `env` object, building the second class's methods overwrote the *same* environment's `super` binding that the first class's methods had already captured by reference. Concretely: `class A {}`, `class B extends A { greet(){ return super.greet()+'B'; } }`, `class C extends B { greet(){ return super.greet()+'C'; } }` — building `C` retroactively changed what `super` resolved to *inside B's own `greet`*, from `A.prototype` to `B.prototype`, so calling `new C().greet()` recursed into `B.greet` calling itself forever. Fixed by giving each class its own dedicated child environment (`classClosureEnv`) to bind `super`/`__superCtor` on, so later classes in the same scope can never reach back and change an earlier one's methods.
   - **A related, compounding half of the same bug:** the *synthetic* default constructor auto-generated for a derived class with no explicit `constructor()` (its entire body is `super(...arguments)`) still used the plain outer `env` as its closure even after the above fix, since it wasn't updated to match. A derived class two levels deep with neither level defining its own constructor (`class B extends A {}`, `class C extends B {}`, both just method-only) threw `"super() called outside of a derived class constructor"`, because when C's synthetic `super()` call ran B's synthetic constructor body, that body's own `super()` (needed to reach A) had no environment carrying `__superCtor` at all. Fixed by giving the synthetic constructor `classClosureEnv` too. Also fixed the same manually-inlined `super()`-call machinery's own parameter binding (`pfn.params.forEach(...)`, the exact naive positional-zip bug fixed everywhere else in the engine two rounds earlier in the same day) to go through `bindParams()` instead.
   - **A further, distinct half:** static methods need `super` bound to the parent *class object* (for `super.staticMethod()`), not the parent's *instance prototype* (what regular methods need) — reusing one shared binding for both meant `super.staticMethod()` always resolved against the wrong target and returned `undefined`. Added a second, separate `staticClosureEnv` with the class-object binding, used only for `static` members.

7. **Private fields/methods (`#name`) were not lexed at all, and silently mis-parsed into two unrelated garbled members instead of throwing.** The lexer's character dispatch had no case for `#`, falling to the generic `Illegal` token — but `parsePropertyKey()`'s own fallback permissively accepts *any* token's raw text as a property name, so `#value;` parsed as one field literally named `"#"` (value `null`) immediately followed by a second, completely unrelated field named `"value"` — no error, just quietly wrong. Lexed `#` plus a following identifier as a single ordinary `Identifier` token whose name includes the `#`, so declarations, reads, and writes all flow through the exact same Identifier/property-key machinery as every other property — a deliberate simplification that does not enforce real member-privacy (`obj.#x` is still reachable from outside its class here, unlike real JS's syntax-level restriction), flagged in-code as a known ceiling rather than silently pretending to be complete.

8. **A class instance's own `toString()`/`valueOf()`/`Symbol.toPrimitive` was never consulted during string/number coercion** — template-literal interpolation, `+`, and unary `+`/`-`/`~` all coerced with the generic, *shape-based* `toString()`/`toNumber()` (this engine's low-level fallback for "what does this object look like internally"), which has no way to call a user-defined method and so always fell back to the same `[object Object]`/`NaN` regardless of what the class actually defined. Added `jsToPrimitive()`/`jsToString()` (checking `Symbol.toPrimitive` first per spec, then `valueOf`/`toString` in hint-appropriate order) and wired them into template literals, the `+` binary operator (evaluating both operands with default-hint ToPrimitive *before* deciding string-concat vs. numeric-add — the old code checked `typeof left === 'string'` *before* any coercion, so an object operand's own `toString` was never even tried), and unary `+`/`-`/`~`.
   - **A side effect this exposed, not a regression:** this engine's typed arrays already had a fully correct, spec-compliant `toString()` (comma-joining elements, matching real `%TypedArray%.prototype.toString` — inherited from `Array.prototype.toString` per spec) — it just wasn't reachable via `+`/template coercion until now, so two pre-existing tests asserting `'' + new Uint8Array(4) === '[object Uint8Array]'` were themselves encoding the old, unreachable-method bug as their expected value. Updated both tests to the real, now-correctly-produced value (`'0,0,0,0'`).

## Notes
- The stack-overflow bug (root cause 6) is the clearest illustration all session of why "does the fix generalize to more than the one symptom in the ticket" matters: the *first* fix attempt (giving each class its own `classClosureEnv`) fixed the crash but immediately surfaced a *second*, previously-masked bug in the exact same area (the synthetic constructor's stale closure) — the crash had been hiding a correctness bug behind an even louder failure mode.
- All nine of this round's bugs were found from a single ~40-line probe script covering ordinary, everyday class usage — none of them required an exotic or edge-case pattern to trigger. This is consistent with the pattern noted in this session's earlier rounds: foundational bugs in rarely-exercised code paths (here, "more than one related class in a file") hide in plain sight until something finally forces the path to run.
- Root cause 6's fix required distinguishing THREE separate super-binding needs that had previously been conflated into one: instance-method `super` (→ parent prototype), static-method `super` (→ parent class object), and per-call constructor `super()` (already correctly isolated per-call in `evalNew`, and left unchanged). Getting this distinction right — rather than just making the existing single binding "less shared" — is what made the static-super fix (a separate, smaller bug also found and fixed here) possible without re-breaking the instance case.
- `extends Array` (subclassing a built-in) remains a known, undocumented-in-code gap, deliberately not fixed this round: it needs the built-in's own constructor logic and the derived instance's shape to genuinely merge, which is a materially larger change than anything else in this document and is a comparatively rare real-world pattern next to ordinary user-class inheritance.
- All scratch investigation files (the standalone harness and a `probe/` directory of ad-hoc repro scripts) were deleted before committing. One unrelated, pre-existing tracked file (`logcat.txt`, an Android log dump) was accidentally caught by an overly broad cleanup command and immediately restored via `git checkout HEAD --` before it could reach a commit — a reminder to scope cleanup deletions to files this session actually created, not glob patterns.
