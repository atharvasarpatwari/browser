# JS Engine Round 6 — Static Blocks, `Array.from`, and `new.target` Were All Broken or Missing

**Date:** 2026-09-16
**Session:** Direct continuation of Round 5 ("keep going, find more real gaps to fix"), same day. Broadened the probe surface beyond prototypes/functions into object-literal accessors, spread, array/object statics, computed class fields, static blocks, optional chaining on arrays, WeakMap, Proxy, Reflect, `new.target`, and `Symbol.hasInstance`.
**Status:** Completed

---

## Summary
A broad probe across object/array features surfaced a script that crashed entirely with an uncaught native exception — the same try/catch-escape bug class fixed repeatedly this week, this time triggered by a `static { ... }` class block. Investigating found `static` initialization blocks were **entirely unimplemented**: the parser had no case for `static {`, so it either failed to parse outright or silently mis-parsed the block's contents as a property key, discarding its side effects. Fixing the parser surfaced a second bug: a class's own name wasn't bound inside its own static field initializers or static blocks, breaking the common self-referencing singleton idiom (`class Singleton { static instance = new Singleton(); }`). Separately, `Array.from` only ever handled real array sources — strings, array-likes (`{length:3, 0:'a',...}`), `arguments`, Sets, Maps, generators, and custom iterables all silently produced `[]`. And `new.target` was not just unimplemented but actively mis-parsed: `new.target` was read as `new` applied to `.target`, producing garbled, nonsensical values instead of a clean error or the right answer. Fixed all of it at the root; folded into a new 9-check `static-blocks-array-from-new-target` sweep case (102/102 checks green). Full suite: zero regressions.

## Root Causes

1. **`static { ... }` blocks were entirely unimplemented in the parser — not even represented in the AST.** `parseClassBody`'s `static` branch unconditionally called `parsePropertyKey()` right after consuming `static`, assuming a member name always followed; when the next token was `{` instead, this mis-parsed the block's contents as if they were a key expression, ranging from an outright `SyntaxError` (a class whose *only* member is a static block) to silently discarding the block with no effect (when it happened to parse as some other valid-looking member by accident, e.g. following a real field declaration). Added a dedicated `StaticBlock` AST node, taught the parser to recognize `static {` before falling into property-key parsing, and taught `buildClassObject` to execute it immediately, in declaration order among the class's other static elements, with `this` bound to the class — exactly where the static field initializer already runs, right above it in the same loop.
2. **A class's own name wasn't bound inside its own static field initializers or static blocks.** `class Singleton { static instance = new Singleton(); }` — an extremely common self-referencing singleton pattern — saw its own name as `undefined` inside that initializer, since `Singleton` isn't bound in the *outer* scope until the whole class declaration finishes, and nothing bound it in an *inner* scope either (the way a named function expression binds its own name for exactly this reason). Fixed by binding the class's own name to the class object in both `classClosureEnv` and `staticClosureEnv` right where those scopes are created, and additionally routing static field initializers through `staticClosureEnv` (they previously closed over the plain outer `env` directly, so they also couldn't see `super` inside a static field initializer — the same gap, same fix).
3. **`Array.from` only ever handled real array sources; every other spec-mandated source produced `[]`.** Its own implementation checked `srcObj.type === 'array'` and returned an empty array for anything else — so a string, a plain array-like object (`{length:3, 0:'a',...}`, the shape of an `arguments` object or a DOM `NodeList`-style object), a `Set`, a `Map`, a generator, or any custom `Symbol.iterator`/`.next()`-based iterable all silently converted to `[]` instead of throwing or working, which is easy to miss precisely because it doesn't look like an obvious crash. Implemented a real `iterableToArray()` helper mirroring the interpreter's own `forOfValues` iterable-draining logic (array shape, `Symbol.iterator` protocol, Map/Set's own `entries()`/`values()`, a generic `.next()`-based iterator) plus one extra fallback `for-of` doesn't need: a non-iterable array-like object, which `Array.from` explicitly supports converting. Needed a small supporting fix: `toPropertyKey()` (used to turn a `Symbol.iterator` value into its internal string key) was a private helper local to `interpreter.ts` with no Interpreter instance available to this native function — exported it from `values.ts` instead of duplicating its logic.
4. **`new.target` was not just unimplemented but actively mis-parsed, producing garbled nonsense instead of a clean error.** With no special-case handling, `new.target` was parsed as an ordinary `new` expression whose callee parse started at `.target` — a token sequence that doesn't validly start an expression — silently producing corrupted AST/values rather than a `SyntaxError`; in practice this showed up as extra, nonsensical arguments appearing in unrelated `console.log` calls near the `new.target` use. Added a dedicated `NewTargetExpression` AST node, parsed as a `new.target` meta-property, and evaluated via an internal `__newTarget` environment binding set at every construction site: `evalNew`'s plain-function-constructor and class-constructor branches set it to the constructor being invoked, `evalCall`'s ordinary (non-`new`) call path explicitly sets it to `undefined` (shadowing any outer value, so a plain call from inside a constructor doesn't incorrectly inherit `new.target`), and arrow functions never set their own (matching how they never set their own `this`), so `new.target` inside one correctly resolves through the closure chain to the nearest enclosing ordinary function. A second, compounding gap in the same area: `new.target` must stay the *originally invoked, most-derived* class throughout an entire `super()` chain — the `super()` call handler builds a fresh environment rooted at the parent constructor's own closure, which had no idea what `new.target` was outside it, so it had to be explicitly carried over rather than left to default to `undefined`.

## Notes
- The static-block crash was found the same way as this week's other try/catch-escape bugs: a probe crashed with zero console output past a certain point, confirming an uncaught native exception rather than a script-level bug — but this time the underlying cause was a genuine parse-time `SyntaxError` in one specific shape (a static-block-only class), which can never be caught by any runtime `try`/`catch` in the same script regardless of engine correctness (a parse error happens before any code runs) — worth distinguishing from an actual escape-past-`try/catch` bug, which this specific manifestation wasn't, even though the *symptom* (script aborts entirely, unhandled) looked identical at first.
- Confirmed, but explicitly **not fixed this round** (documented here rather than silently left for a future session to rediscover): `Proxy` traps (`get`/`set`/`has`/...) don't fire at all — `new Proxy(target, {get(){...}})` returns something that behaves like a plain passthrough rather than invoking the handler; `Reflect` doesn't exist as a global at all; `Symbol.hasInstance` isn't consulted by the `instanceof` operator; and the legacy `__proto__` accessor isn't implemented (though its modern replacement, `Object.getPrototypeOf`/`setPrototypeOf`, was fixed in Round 5). These are real gaps, but each is a substantial standalone feature rather than a quick root-cause fix, and none of them reproduce the "confidently wrong instead of cleanly failing" pattern that's been this week's priority — flagged for a future round rather than attempted here under the same time budget as the rest of this session's fixes.
- `Object.keys`/`Object.values`/`Object.entries` were checked directly against a plain-function-constructed instance with an inherited prototype property and were already correct (own enumerable keys only, no inherited leak) — worth confirming explicitly given how many *other* enumerability-adjacent bugs this week's rounds found (the `for-in` fix in Round 5, the class-member-enumerable-flag fix also in Round 5).

## Verification Steps
1. Broad probe across object-literal accessors, spread, array/object static methods, computed class fields + static blocks, optional chaining on arrays, `WeakMap`, `Proxy`, `Reflect`, `new.target`, and `Symbol.hasInstance` — most passed, but the whole script crashed partway through with zero output past a certain point.
2. Bisected by removing blocks one at a time until a minimal repro emerged: a class containing *only* a `static { ... }` block failed to parse entirely (`Expected LBrace, got Semicolon`); a class with a field *then* a static block parsed but silently discarded the block's effect.
3. Added a dedicated `StaticBlock` AST node and parser case, and interpreter execution for it; re-verified the static block's side effect actually applies and runs with the correct `this`.
4. Testing self-referencing static initializers (the singleton idiom) surfaced the class-self-name-binding gap; fixed by binding the class's own name into its static/instance closure environments, and routing static field initializers through the same closure environment as static methods and blocks (they'd been using a separate, more limited one).
5. Re-ran the full probe with the crash fixed — surfaced `Array.from` returning `[]` for a string, an array-like object, a `Set`, and a `Map` (a mapped real array worked). Implemented a proper iterable-draining helper mirroring the interpreter's own `for-of` logic, verified against strings, array-likes, `arguments`, generators, custom iterables, `Set`, and `Map`.
6. `new.target` printed garbled, multi-value nonsense instead of a clean boolean — traced to the parser having no case for the meta-property syntax at all, mis-parsing `.target` as a constructor callee. Added a dedicated AST node and parsing case, plus `__newTarget` environment bindings at every call/construct site; verified `new Foo()` vs. plain `Foo()`, arrow-function inheritance of the enclosing function's value, and correct propagation of the *original* derived class's identity through a `super()` chain (which needed a second, compounding fix once the base case worked, since the `super()` call handler builds a fresh environment that doesn't inherit anything from the caller by default).
7. Folded all of the above into a new 9-check e2e sweep case, ran the full `npx vitest run` (0 regressions) and the complete Electron e2e suite after rebuilding the web bundle (5/5 specs, 102/102 sweep checks), and deleted all scratch investigation files before this final verification pass.
