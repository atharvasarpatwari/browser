# JS Engine — Try/Catch Escape Bug Uncovers 17 Real Gaps (classList, innerHTML, regex literals, Event, and more)

**Date:** 2026-09-15
**Session:** Built a real-fixture JS/DOM API sweep (three HTML pages exercising core-js, DOM/events, and async/collections APIs, each pixel-sampled through the real Electron app), which immediately showed every check as "untouched" across all three fixtures. Root-caused that to a single foundational bug — internal engine-thrown `TypeError`s bypass every sandboxed `try`/`catch` — then kept pulling on the thread: fixing it, and fixing the newly-visible failures, and fixing the failures *those* fixes exposed, across four passes until the sweep's 45 checks were all green.
**Status:** Completed

---

## Summary
Started from "keep going, find more real gaps" and built a JS/DOM equivalent of this session's earlier CSS pixel-sweeps: three fixture pages, each asserting a battery of JS/DOM behaviors by turning a grid of marker `<div>`s green (pass) or red (fail), sampled via the real rendered canvas in the actual Electron app. The very first run showed **every single check on every fixture as untouched grey** — the sweep's own signal was broken, not 45 simultaneous failures. Root-causing that (via isolated `runJS()` repros outside Electron/Playwright, bisecting scripts, and adding temporary stack-trace logging) found a single foundational bug: any internal validation error the interpreter throws as a native TS `TypeError`/`Error` (rather than wrapping it as the engine's own catchable `JSError`) unwinds straight past *every* level of a sandboxed script's `try`/`catch`, silently aborting the rest of that script's execution — not just the one `try` block that happened to trigger it. Fixing that alone turned the "all grey" sweep into a real signal, which then surfaced 16 more genuine, independent gaps: `classList` was entirely unimplemented, `innerHTML`'s setter was a no-op, `children`/`firstChild`/etc. were one-time snapshots that never reflected later mutations, regex literals evaluated to their own source text instead of a real `RegExp`, `Event`/`CustomEvent` had no constructors at all, and more. Each was root-caused with the same isolated-repro methodology and fixed at its source; the final sweep run is 45/45 green with zero regressions across the full unit and e2e suites.

## Root Causes

1. **Internal engine-thrown native errors bypassed every sandboxed `try`/`catch`, aborting the rest of the script.** `execTry` (the interpreter's implementation of a user's `try { } catch(e) { }`) only recognizes the engine's own `JSError` class as catchable; anything else re-throws unconditionally (`interpreter.ts`'s `execTry`). Several places threw a *native* TypeScript `TypeError`/`Error` directly — `evalMember`/`evalCall` on `x.y` where `x` is `undefined`/`null`, illegal `super()`, and (separately) `values.ts`'s `callJSFunction` / `interpreter.ts`'s two native-function call sites converting a caught native exception via `new JSError(err.message)` — that last one actually *did* produce a `JSError`, but by passing a bare string as its value it lost the distinction from a real thrown `Error` object once fixed (see root cause 17). The real, uncaught native throws meant a page script doing something as ordinary as `foo.bar()` where `foo` turned out to be `undefined` didn't just fail that one `try` block — it silently killed every remaining statement in the `<script>` tag, with nothing visible to the page (no `onerror`, nothing). Root-caused via an isolated `runJS()` repro outside Electron (bypassing Playwright entirely for fast iteration), binary-searching the failing fixture down to a five-line reproduction, then adding a temporary debug log in `execTry`'s "not a JSError, re-throw" branch to capture the real stack trace, which pointed at `getPropertyValue`. Fixed by adding a shared `jsError(name, message)` helper that builds a proper Error-shaped `JSObject` and wraps it as `JSError`, and using it at all six raw-native-throw sites in `interpreter.ts` (`evalMember`, the member-call-callee check, illegal `super()`, and the two "convert a caught native exception" sites) plus the equivalent in `values.ts`'s `callJSFunction`. Also improved the "Cannot read properties of X" messages to include `(reading 'prop')` like real V8, since the property name was already being computed nearby.

2. **`Number` had zero static methods or constants.** `Number` was built via `createNativeFunction('Number', ...)` — a bare callable `JSFunction` with no `.properties` map at all — so `Number.isInteger`, `.isFinite`, `.isNaN`, `.isSafeInteger`, `.parseFloat`, `.parseInt`, `.EPSILON`, `.MAX_SAFE_INTEGER`, etc. were all simply absent (`index.ts`). This is exactly the kind of gap the try/catch bug above was hiding: `Number.isInteger(5.0) === true && ... && Number.isFinite(Infinity) === false` threw immediately on the `Number.isFinite` lookup, and that throw silently killed the rest of the `core-js` fixture's script — which is why *all 20* of that fixture's checks showed grey, not just the one exercising `Number`. Fixed by rebuilding `Number` the same way `Array`'s fuller constructor is built elsewhere in the file: a `createObject(null)` with `type: 'function'`/`callable: true`/`nativeFn` for the `Number(x)` conversion call, plus the missing static methods and constants as real properties.

3. **`getPropertyValue`'s generic object fallback crashed outright when `.properties` was missing.** While root-causing #2, the *first* attempted fix (adding `Number.isFinite` alone) still silently did nothing — a debug log inside the new method never printed, meaning the property lookup itself was throwing before ever reaching it. `getPropertyValue`'s function-object special case only recognizes `length`/`name`/`arguments`/`caller`/`prototype`; any other key (like `isFinite`) "falls through to normal property lookup", `const desc = o.properties.get(key)` — and a bare `createNativeFunction` result (like the *old* `Number`) has no `.properties` map, so this crashed with `Cannot read properties of undefined (reading 'get')` — a genuine engine bug (not a validation throw), and, per root cause 1, one that also escaped every `try`/`catch` around it. Fixed defensively with `o.properties?.get(key)`, so a function-like object missing a given property now correctly resolves to `undefined` instead of crashing the whole script — a safety net for this exact class of gap regardless of which specific global is missing which specific method next.

4. **`classList` did not exist anywhere in the engine.** Not in `dom-bindings.ts`, not anywhere in `src/browser/js/` or `src/browser/` — `el.classList` was `undefined` for every element, so `el.classList.add(...)` (one of the single most common DOM patterns on the real web) threw immediately. Implemented a `buildClassList(el, domTree)` DOMTokenList — `add`/`remove`/`toggle(force)`/`contains`/`replace`/`item`/`toString`/`length`/`value` — backed by the same `class` attribute as `className`, recomputing the token list fresh on every method call (rather than snapshotting once) so `add` then `contains` on the same captured reference see each other's effect.

5. **`Array.prototype.includes` used `===` instead of SameValueZero, so `[NaN].includes(NaN)` was `false`.** Also surfaced, while tracing this: `index.ts` contains an entire second, *dead* copy of the array-method table (`arrProtoMethods`, built into an `arrayProto` object) that is never actually consulted — `values.ts`'s `attachArrayMethods` attaches its own, separate implementations directly onto every array *instance* at creation time, which shadow the prototype-based ones before they're ever reached. Confirmed by adding a debug log to the `index.ts` copy's `indexOf` and seeing it never fire. Fixed the real, active implementation (`values.ts`'s `arrayIncludes`, previously just `arrayIndexOf(...) !== -1`) to use SameValueZero comparison; left the shadowed dead copy in `index.ts` alone (out of scope for a bug-fix pass — flagged as a separate cleanup candidate, not fixed here).

6. **`String.prototype.at()` and `Array.prototype.at()` did not exist.** Added both, with standard negative-index-from-end semantics and out-of-bounds returning `undefined`.

7. **Regex literals evaluated to their own source text, not a real `RegExp` object.** `evalLiteral` special-cased any `Literal` node whose `.value` carries AST metadata (`'type' in expr.value`) by returning `expr.raw` — the literal's *source string* — with no check for what kind of literal it actually was. A `/pattern/flags` regex literal has exactly this shape, so `/(?<year>\d{4})-(?<month>\d{2})/.exec(...)` was really `"/(?<year>\\d{4})-(?<month>\\d{2})/".exec(...)` — calling `.exec` on a *string*, which doesn't have that method. Only `new RegExp(pattern, flags)` ever produced a working regex object; every regex *literal* in every script silently didn't work, cascading into named-capture groups, `matchAll`, `.replace(regex, ...)`, `.match(regex)`, and `.split(regex)` all failing wherever a literal (rather than a constructor call) was used — which is the overwhelming majority of real-world regex usage. Fixed by making `evalLiteral` (now taking `env`) route a `RegExpLiteral` value through the *same* `RegExp` global constructor's `nativeFn` that `new RegExp(...)` already uses, so a literal produces the exact same object shape (and thus gets full `.exec()`/`.test()`/named-groups support) instead of a hand-rolled parallel path.

8. **`String.prototype.replace()` didn't support regex patterns or function replacers at all.** Once literals produced real regex objects (#7), `'a1b2'.replace(/\d/g, fn)` still failed a level deeper: the implementation did `(obj as string).replace(toString(a[0]), toString(a[1] ?? ''))`, coercing *both* the pattern and the replacement through generic `toString()` — a regex object stringifies to something useless, and a function stringifies to something equally useless, so real regex-plus-callback replacement never worked, only literal-string-to-literal-string. Same underlying issue affected `.match()`, `.search()`, and `.split()`, which built their own regexes via `new RegExp(toString(a[0]))` — again stringifying a real regex object incorrectly instead of using its native `RegExp` directly. Added a shared `toNativeRegex()`/`stringReplaceImpl()` pair that checks for a real regex object first (extracting its underlying native `RegExp` via the same `nativeRegExp` field `RegExp.exec`/`.test` already use) and bridges a JS-function replacer into a real native replacer callback via `callJSFunction`, and used them consistently across `replace`, `match`, `search`, and `split` (both of the two duplicated `strMethods` tables in `interpreter.ts` — the second, for plain non-call property reads, had also drifted to be missing `search`/`matchAll` entirely, fixed to match).

9. **`String.prototype.replaceAll()` and `.matchAll()` did not exist.** Added both — `replaceAll` reusing the same regex/function-replacer bridge as `.replace()` (forcing the `g` flag when given a non-global regex, matching the real spec requirement), `matchAll` iterating a forced-global regex's native `matchAll()` and building index/input-bearing match-array objects the same shape `.exec()` already produces.

10. **`JSON.stringify()` silently ignored its replacer-function argument.** The implementation only ever read `args[0]`; a replacer function passed as `args[1]` was never called, so `JSON.stringify({a:1,b:2,c:3}, (k,v) => k==='b' ? undefined : v)` stringified all three keys instead of omitting `b`. Threaded an optional `replacerFn`/`holder`/`key` through the recursive `jsonStrify`, calling the replacer (when present) on every value — including the top-level one, per spec — before the existing type-dispatch logic runs.

11. **Element-level `querySelector`/`querySelectorAll` did not exist; `Element.matches()` used a broken whole-document heuristic; `Element.closest()` did not exist.** `querySelector`/`querySelectorAll` were only ever attached to `document`, never to individual elements, so `someElement.querySelectorAll(...)` was `undefined`. `matches()` existed but was implemented as `domTree.querySelector(sel) === el` — comparing the element against the *first document-wide match* for the selector, which is only coincidentally correct when the element happens to be that first match. Added element-scoped variants to `DomTree`/`IDomTree` (`querySelector(selector, scopeRoot?)`/`querySelectorAll(selector, scopeRoot?)`, excluding the scope element itself from its own results, matching `Element.querySelector`'s spec behavior which differs from `Document.querySelector`'s) and a proper `matches(element, selector)` that checks only that element via a newly-exported `matchesSelectorString()` in the CSS5 selector module. Implemented `closest()` by walking `el` and its ancestors calling the new `matches()` on each.

12. **`element.innerHTML`'s setter was a plain-value snapshot — assigning it did nothing to the real DOM.** `obj.properties.set('innerHTML', { value: getInnerHTML(el), writable: true, ... })` had no `setter` at all, so `el.innerHTML = html` fell through the interpreter's assignment fallback (no setter found → just overwrite the plain JS property) and silently changed nothing about the real element's children — the getter then dutifully echoed back whatever string was last assigned, making the bug invisible from the JS side alone. Since the DOM/events fixture (and, presumably, most real pages) builds its test markup via `container.innerHTML = '...'`, this one bug alone explained the majority of that fixture's failures. Fixed with a real setter that clears the element's existing children and parses the new HTML into a live subtree via a new `DomTree.parseFragment()` (parses the string as its own small document via `HtmlParser`, then lifts the parsed body's children out and converts each into a real, indexed `DomNode` — the same conversion `buildFromHtml` uses internally, exposed for fragment reuse without resetting the whole document's indices) and attaches it with the existing `appendChild`.

13. **`children`/`childNodes`/`parentNode`/`firstChild` were snapshots taken once at wrap-time; `lastChild`/`nextSibling`/`previousSibling` didn't exist.** The exact same "plain value computed once" anti-pattern this session's earlier CSS/`.style` work had already found and fixed for `element.style` was present here too, for the DOM tree's own shape: any JS reference obtained *before* a mutation (`appendChild`, the `innerHTML` fix above, `insertBefore`, ...) never saw that mutation reflected in `.children`/`.firstChild`/etc. afterward, since `wrapElement()` caches one JS object per underlying element and these were plain non-getter properties computed at the moment of that first wrap. Converted all four to live getters reading `el.children`/`el.parent` fresh on every access, and added `lastChild`/`nextSibling`/`previousSibling` (previously missing outright) as the same kind of live getter.

14. **`Event`, `MouseEvent`, `CustomEvent`, and `KeyboardEvent` had no constructors.** `addEventListener`/`dispatchEvent`/the whole three-phase capture-target-bubble dispatch machinery, and even a `createEventObject()` factory building a fully-featured event object (bubbles/cancelable/`preventDefault`/`stopPropagation`/etc.), all already existed — but nothing exposed `Event`/`MouseEvent`/`CustomEvent` as constructible globals, so `new Event('click')` resolved to no global at all and produced a mostly-empty fallback object whose `.type` was `undefined`. Every `addEventListener('click', ...)` + `dispatchEvent(new MouseEvent('click'))` pattern — one of the most fundamental things JS does — silently never fired, since dispatch matches listeners by `event.type` and `undefined` matches nothing. Registered all four as globals built from the existing `createEventObject()`, with `CustomEvent` additionally copying `options.detail` onto the built event.

15. **`.remove()`, `.append()`, `.prepend()`, `.before()`, `.after()`, and `.dataset` did not exist.** All standard, extremely common modern DOM APIs; none were implemented anywhere in `dom-bindings.ts`. Added all five node-mutation methods (converting any non-DOM-node argument to a text node, per spec, and preserving left-to-right argument order for the three variadic ones) plus `dataset`, a DOMStringMap-shaped object rebuilt fresh on every access from the element's current `data-*` attributes (camelCase getters/setters mapped back to the kebab-case attribute).

16. **`setTimeout`/`setInterval` discarded every argument past the delay.** `setTimeout(fn, delay, ...extraArgs)` is standard and commonly used to avoid an extra closure; the real, active implementation (`event-loop.ts`'s `bindTimers` — a second, dead copy also exists in `interpreter.ts`'s own internal fallback `createGlobalEnv`, not used by the real page pipeline) always invoked the callback with `callJSFunction(fn, _this, [])`, an empty args array, silently dropping anything passed after the delay. Fixed both `setTimeout` and `setInterval` to capture `args.slice(2)` and forward it.

17. **`EventLoop.runOnce()` selected the next due timer by array/insertion order, not by earliest deadline.** `this.tasks.findIndex(t => now - t.scheduledAt >= t.delay)` picks the *first* task in the array that happens to already be due — not the one with the soonest deadline. Scheduling a 40ms timer and then a 5ms timer and letting both become due within the same processing check (plausible whenever the driving loop's polling cadence is coarser than the gap between two timers, e.g. `runAll()`'s busy-spin loop catching up, or a fixed frame-rate tick) fires the 40ms one first purely because it was inserted first — breaking `Promise.race` (whichever promise's timer happened to be scheduled earliest could win regardless of delay) and any other code relying on relative timer ordering. Fixed by scanning all due tasks and picking the one with the minimum `scheduledAt + delay`.

18. **(Found fixing #1) `JSError`'s outer `.message` and the sandboxed `toString()` both mishandled Error-shaped objects.** Making native throws carry a proper `{message, name, stack}` object (root cause 1) had a side effect: `JSError`'s constructor built its own (TS-level) `Error.message` via a generic `toString(value)`, which for a plain object produces `"[object Object]"` — so `RunJSResult.error.message` (what a caller sees for an *uncaught* script error) regressed from a useful string like `"EvalError: ..."` to literally `"[object Object]"`, and the same generic `toString()` is also what the sandboxed `String()`/template-literal coercion calls, so a script doing `catch(e) { String(e) }` got the same useless string instead of `"TypeError: ..."`. Caught by re-running the full `vitest` suite after the fix above (16 failures, all asserting on error message text) — a good reminder to run the full suite, not just the targeted repro, after touching a shared primitive like `JSError`. Fixed by (a) having `JSError`'s constructor prefer an Error-shaped value's own `.message` field over generic stringification, and (b) tagging every Error-shaped object this engine builds (`jsError()`, `callJSFunction`'s native-exception wrapping, and the `TypeError`/`RangeError`/etc. constructors) with `__type_override: 'error'` so the shared `toString()` renders them as `"Name: message"` — matching real `Error.prototype.toString` — instead of falling through to the generic `[object Object]` catch-all.

## Notes
- The methodology throughout mirrored this session's earlier CSS pixel-sweep work: build a real fixture, get a signal from the *actual* rendering pipeline (not a unit test mock), and when the signal looks too broken to be real (45/45 grey), trust that instinct and root-cause the harness/engine bug behind the *signal* before trusting any individual check's result.
- Root-causing root cause 1 (the try/catch escape) needed a standalone `runJS()` harness outside Electron/Playwright entirely — building an `HtmlParser`+`DomTree`+`runJS()` pipeline directly (matching `tests/integration.test.ts`'s existing `executeInlineScriptsSimple` pattern) made each iteration near-instant compared to a full Electron relaunch, and made it easy to add temporary `console.log`s directly in engine TypeScript (captured by Node's own stdout) rather than fighting with the sandboxed page's own console routing.
- Several of the 18 root causes were only reachable *because* earlier ones in the same session were fixed — e.g. `Number`'s missing statics (#2) was invisible until the try/catch escape (#1) stopped masking it as "all 20 core-js checks are grey"; `innerHTML`'s dead setter (#12) was invisible until regex literals (#7) and `classList` (#4) stopped absorbing all the attention as the obvious first failures. This is expected for a foundational bug like #1 — fixing it doesn't just fix itself, it turns every *other* latent bug's symptom from "silent, total script failure" into "one specific, attributable check fails," which is what made the rest of this list findable at all.
- `Array.prototype.includes`'s dead-code duplicate (root cause 5) and `interpreter.ts`'s dead internal `createGlobalEnv`/`setTimeout` (root cause 16) are real, pre-existing shadowed-code situations, not something this session's fixes need to also delete — flagged here rather than touched, since deleting them is an unrelated cleanup, not a bug fix.
- All scratch investigation files (`scratch-run-js.mjs`, `scratch-extract-scripts.mjs`, `scratch-run-parser.mjs`, three `scratch-script-*.js` fixtures, and a `slices/` directory of ad-hoc isolated repros) were deleted before committing; the one genuinely valuable e2e test (the JS/DOM sweep itself) was promoted from `tests/e2e/_js-dom-sweep.spec.ts` to a permanent `tests/e2e/js-dom-api-sweep.spec.ts`.
