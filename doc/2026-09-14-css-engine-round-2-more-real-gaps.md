## Summary
Five more real, independent engine bugs found and fixed — one of them (a rasterizer state leak) turned out to affect *any* page using `overflow:hidden`/`scroll`/`auto`, not just the fixture that surfaced it, since it corrupts every subsequent repaint of the same tab. One test (`:nth-child`) turned out to be a test-authoring mistake, not an engine bug, and is documented as such. All 17 fixtures / 42 checks in the merged sweep pass; full unit and e2e suites stay green.

## Root Causes
1. **`grid-template-columns: repeat(auto-fill, ...)` (and `auto-fit`) collapsed to a single, effectively-zero-width column.** `parseTrackList()` correctly captured `{type:'auto-fill', sizes:['50px']}` for these, but every caller did `defs.map(d => d.value)`, and for an auto-fill/auto-fit def, `.value` is just the garbled leading token of the raw `repeat(auto-fill,...)` text — not a valid track size. `resolveTrackBase()` then silently fell back to `parseFloat(garbage) || 0`. Fixed by adding `expandTrackDefs()`, which resolves how many copies of the repeated track list actually fit the container (sizing `minmax()` off its minimum bound) and expands them into real per-track size strings before layout ever sees them.
2. **Multi-column layout (`column-count`/`column-width`) computed geometry nobody used, then actively corrupted the page.** `MultiColumnFormattingContext.resolve()` only ever computed abstract column boxes (`getColumns()`); nothing called it outside `layout-engine.ts` itself (confirmed via a global search — `getMultiColumnContext` had zero external callers). Children stayed exactly where normal block stacking put them (one full-width column), while the container's own height was set to `mcCtx.getTotalHeight()` — a single column's worth — silently shrinking the container and pushing every element that follows it on the page into the wrong position. Fixed properly, not just patched: children are now laid out at the actual column width from the start (not full width then shrunk), packed into real column boxes by greedy height-based placement, and every descendant of a repositioned child is translated along with it (layout boxes are absolute, so moving a child without its subtree would leave grandchildren rendering at their stale position). Content that's plain text/inline rather than discrete element children (nothing to pack) falls back to the original balanced-height estimate instead of collapsing to a phantom 0px.
3. **`@container`/`@supports`/`@media` blocks could lose cascade ties to an earlier, same-specificity rule declared before them.** Each of these at-rules parses its nested body with a **brand-new** `CssParser` instance, whose own `sourceOrder` counter restarts at 0 — so a style rule three rules into the real document could carry `sourceOrder: 0`, identical to (or lower than) a plain top-level rule declared *before* it. The cascade's tie-break ("same specificity → higher `sourceOrder` wins") then let the earlier rule win incorrectly. This exact risk was flagged-but-unconfirmed in the prior session's `@layer` fix (masked there because layer-index comparison short-circuits before the cascade ever reaches the broken `sourceOrder` tie-break); it's real, and affects any same-specificity competition between a top-level rule and a later matching `@container`/`@supports`/`@media` block. Fixed by offsetting every rule's `sourceOrder` inside a parsed block by its own top-level position (scaled well above any realistic per-block rule count), composing correctly at any nesting depth since each level's own rules are already self-offset before the level above applies its own offset.
4. **`overflow: hidden`/`scroll`/`auto` (and any other shorthand) set via an inline `style="..."` attribute silently did nothing.** `expandShorthands()` — which turns `overflow` into `overflow-x`/`overflow-y`, `margin` into its four sides, etc. — was only ever applied to declarations from `<style>` tags, never to inline declarations. `overflow-x`/`overflow-y` therefore stayed unset on the raw `overflow` value and got force-filled with their own initial value (`'visible'`) by `setInitialValues()`'s registry pass — producing a self-contradictory computed style (`overflow: hidden` alongside `overflow-x: visible`). Every caller that read `style.get('overflow-x') ?? style.get('overflow') ?? 'visible'` picked up the bogus `'visible'`, since `??` only falls through on `null`/`undefined`, never on an already-present `'visible'` — silently defeating inline `overflow` everywhere (paint-engine's clip-rect and layout-engine's scroll-container setup alike). Fixed at the root by running inline declarations through `expandShorthands()` too, plus adding the `overflow` shorthand itself (never handled at all, for either inline or stylesheet rules).
5. **A `clip` from one page's paint permanently corrupted every later repaint of the same tab.** `Rasterizer.rasterize()`/`GpuRasterizer.rasterize()`/`rasterizeAsync()` reused `this.state` (which holds the active clip rect, transform, and alpha) across calls without ever resetting it, and `renderStackingContext()`'s `save`/`restore` bracketing only wraps opacity/transform groups — never a plain `overflow:hidden` clip. So a `clip` pushed during one `rasterize()` call (e.g. a page's first paint) stayed active in every subsequent `rasterize()` call on that same engine instance — including that *next* call's own full-canvas background fill — clipping content with no relation to the element that originally set it. This is why the `overflow-hidden-clip` fixture failed specifically in the live app but not in an isolated single-shot repro of the same layout: `page-renderer.ts` paints a page twice (before/after script execution), and the second pass inherited the first pass's leftover clip. Fixed by resetting clip/transform/alpha state (and the save stack) at the start of every `rasterize()`/`rasterizeAsync()` call, in both the software and GPU rasterizers — each call is a fresh frame and should never inherit state from the last one.

## Notes
- **`:nth-child()`'s apparent failure was a test-authoring bug, not an engine bug.** The first draft of the `nth-child-formula` fixture put its `<style>` tag inside `<body>`, as a sibling of the counted `.item` divs. Per spec, `:nth-child()` counts *all* element siblings in the DOM tree, including `<script>`/`<style>` — exactly like a real browser — so the `<style>` tag legitimately shifted every div's position by one, flipping odd/even. Verified the engine's `an+b` parsing and position counting were both already correct by reproducing the exact sibling-index math outside the browser before touching any source file. Fixed the test (moved `<style>` into `<head>`), not the engine.
- Two boundary-adjacent pixel checks (`aspect-ratio`'s "outside" sample, `logical-properties`' `padding-block` sample) turned out to be rounding-sensitive artifacts once other fixes shifted rendering slightly — confirmed via direct layout-box inspection that the underlying computed values were exactly correct, then widened the sample margins rather than touching engine code. Same class of issue as round 1's `calc()`/`min()` boundary checks.
- Root cause #3's fix only changes *relative* ordering among rules — it does not change which rules match, still leaves `@container`'s condition evaluated against the page viewport rather than the actual nearest `container-type` ancestor's size (a pre-existing, documented architectural simplification: `evaluateContainerQuery()` has no per-element context available at the stylesheet-flattening stage where it currently runs). Real container-query sizing would need per-element evaluation during cascade matching, not stylesheet-level flattening — a larger change deliberately out of scope here.
- The round-1 and round-2 sweep fixtures were merged into one file (`css-feature-sweep.spec.ts`, 17 fixtures / 42 checks) rather than kept as two near-identical files.

## Verification Steps
1. Extended the real HTTP-server-backed e2e sweep with 9 new fixtures targeting features not covered by round 1: flexbox `gap`/`order`/`flex-wrap`, `::before` generated boxes, `@supports`/`@container` gating, attribute-selector operators, `:nth-child(an+b)`, `overflow:hidden` clipping of absolutely-positioned overflow, `grid-template-columns: repeat(auto-fill, ...)`, and `column-count` multi-column layout.
2. For each of the 6 initial failures, root-caused with a standalone Node repro via `tsx` (either the parsing/layout functions directly, or the full `HtmlParser → DomTree → CssParser → computeComputedStyles → LayoutEngine [→ PaintEngine]` pipeline) before writing any fix — the `:nth-child` case specifically was disproved as an engine bug this way (reproduced the exact sibling-count math and confirmed it matched spec-correct DOM-order counting).
3. For the rasterizer state-leak bug, went a step further than layout inspection: dumped the actual paint command sequence and then the actual rasterized pixel buffer from an isolated single-paint repro (confirming the bug could **not** reproduce there), then dumped a full pixel row from the live Electron app (revealing `alpha:0`, i.e. never-painted, rather than genuinely black) to pin the discrepancy on repeated `rasterize()` calls specifically, not the layout/paint-command logic.
4. Rebuilt the web bundle and reran the full sweep after each fix, confirming the specific check flipped from FAIL to PASS before moving to the next bug; two apparent regressions surfacing mid-session turned out to be resource contention from a concurrently-running full test suite (confirmed by rerunning cleanly) and a genuine unit-test regression (multi-column height went to 0 for text-only content), which was fixed before moving on.
5. Ran the full unit suite and full Electron e2e suite (smoke + fidelity-audit + the merged sweep) after all fixes — all green.
