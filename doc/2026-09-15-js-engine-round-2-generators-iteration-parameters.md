# JS Engine Round 2 — Generators, for-of, Destructured Parameters, and 8 More Real Gaps

**Date:** 2026-09-15
**Session:** Continuation of the same day's try/catch-escape investigation ("keep going, find more real gaps to fix"). Broadened the search past the JS/DOM sweep's own three fixtures into storage, URL/form, and core-language-feature territory, using the same fast-iteration standalone `runJS()` harness established earlier that day.
**Status:** Completed

---

## Summary
Started from a broad probe script exercising `localStorage`, `URL`, `FormData`, form controls, and the History API, then a second probe exercising generators, custom iterators, destructuring, and several newer built-ins. Both surfaced real, high-impact gaps immediately: `URL`/`URLSearchParams`/`FormData`/`TextEncoder`/`TextDecoder` were entirely unimplemented; `function*`/generators failed to even parse; `for...of` only ever worked on array-shaped objects, so `for (const x of someMap)` silently iterated zero times; and — the largest one — every function's parameters were bound with a naive positional zip that only worked for plain identifiers, so a rest, default, or destructured parameter anywhere in the codebase silently bound to a parameter literally named `"undefined"`. Each was root-caused with the same isolated-`runJS()`-repro method as the rest of this session, fixed at its source, and folded into a fourth `language-features` case in the existing `js-dom-api-sweep.spec.ts` (now 65/65 checks green). Full unit and e2e suites confirm zero regressions (two pre-existing tests needed their *expectations* updated, since they asserted the old, spec-incorrect behavior the fix corrected).

## Root Causes

1. **`URL` and `URLSearchParams` did not exist as sandboxed globals.** Used constantly throughout the engine's own TypeScript (`new URL(...)` appears in a dozen files — auth providers, credential matching, CSP checks, resource loading), but never exposed to page scripts at all; `new URL('https://example.com/path?a=1')` silently produced a near-empty fallback object with every property `undefined`. Implemented both by wrapping the real native `URL`/`URLSearchParams` (available as globals in this engine's own Node/Electron-renderer runtime) the same way `RegExp`/`Date` already wrap a native object via a `nativeURL`/`nativeURLSearchParams` field — `URL.prototype.searchParams` returns a live-bound `URLSearchParams` over the *same* native URL, so mutating it moves the URL's query string too, matching spec.

2. **`FormData` did not exist.** Implemented as string-only (no `File`) entries, constructible from a real `<form>` element by walking its DOM subtree for named `input`/`textarea`/`select` controls — checkbox/radio only included when checked, matching spec — reading each control's *current* value/checked off its JS wrapper object (see root cause 4 for why that's where the current value actually lives, not the DOM attribute).

3. **`localStorage`/`sessionStorage`'s `.length` was a snapshot taken once, at first access, and never updated.** `setItem`/`removeItem` correctly wrote through to the backing store, but `.length` was a plain value property computed at wrap time — the same "computed once instead of a live getter" anti-pattern this session's earlier `.style`/`.children`/`innerHTML` fixes already found in `dom-bindings.ts`, here in `web-storage-bindings.ts` instead. Separately, `getItem()`/`key()` returned `undefined` for a missing key/index instead of the spec-required `null`, breaking any code checking `=== null` (or relying on `??` producing a different result than `||` would for a present-but-falsy value) — an existing, deliberate `result === null ? undefined : result` conversion, seemingly on the theory that `undefined` and `null` are interchangeable to callers, which they aren't. Fixed both; updated two pre-existing tests that had encoded the old, incorrect behavior as their expected result.

4. **`Element.name`/`.type` were not reflected attributes — silently invisible to `getAttribute()`, real form-walking code, or `FormData`.** `input.name = 'username'` (or `.type = 'checkbox'`) only ever set an ad-hoc property on the element's cached JS wrapper object (the interpreter's fallback for "assign to a property with no matching getter/setter"), never the real `name`/`type` content attribute both properties are specified as always mirroring in both directions. This one blocked `FormData` (root cause 2) from finding any named control at all, since it has to read the *real* DOM subtree, not JS-wrapper-only ad-hoc state. Fixed by adding real getter/setter pairs backed by `getAttr`/`domTree.setAttribute`, matching the existing `id`/`className` pattern.

5. **Generator function syntax (`function* name() {}`, `function*() {}`) failed to parse at all.** The parser checks `this.is(TokenType.Generator)` in three places (function declarations, function expressions, `yield*`) to recognize the `*` marking a generator — but the lexer's `case '*':` unconditionally produces `TokenType.Star`; `TokenType.Generator` is declared in the token enum and has a string-rendering case, but is never actually emitted by anything. A pre-existing, fully half-wired feature: the AST types, the `generator` flag threading through `createFunction`, and the parser's own checks all assumed a token that never arrives. Fixed by checking for `TokenType.Star` (the token that's actually there) in all three spots instead.

6. **`for...of` only ever handled array-shaped objects — `for (const x of someMap)`, `of someSet`, `of 'a string'`, or `of` any generator/custom iterator silently iterated zero times.** `execForOf` read `.length` and indexed properties directly with no fallback; a `Map`/`Set` (which store entries in internal `Map`/`Set` fields, not indexed properties) or a string (a primitive with no properties at all) simply produced a zero-length loop with no error. Rewrote to extract every value up front via, in order: a real `obj[Symbol.iterator]()` call (draining the resulting `.next()`-based iterator — the first genuinely general iterator-protocol support this engine has had), `Map`/`Set`'s own `entries()`/`values()` methods (found via the interpreter's existing prototype-chain walk in `getPropertyValue`, which the naive fallback bypassed by reading `.properties` directly instead of going through it), plain array indexing (kept, unchanged), and raw string character iteration. Eager extraction (not lazy pulling) is fine here since this engine's own generators (root cause 7) already run eagerly to completion themselves.

7. **Generator *execution* didn't exist even once parsing worked (root cause 5).** `yield` evaluated to its own argument with no suspension effect at all, and calling a generator function ran its body straight through like a normal function, returning whatever it `return`ed (or `undefined`) rather than an iterator object — `gen().next()` was `undefined`. A tree-walking interpreter has no way to genuinely pause mid-body and resume later from that exact point (real suspension needs either a bytecode VM with an explicit resumable frame, or reusing the host language's own generators throughout the whole evaluator) — implemented instead as: run the whole body once, eagerly, to completion, collecting every yielded value in order via a per-call stack of "yield sinks" (`yieldSinkStack`, needed so a generator that itself calls and iterates *another* generator doesn't push into the wrong sink), then hand back a real `{next(), return(), throw()}` iterator that replays the collected values one per `.next()` call. This is faithful for the extremely common "yield a sequence of values" pattern — including `yield*` delegation and `for...of` over a generator, both of which only ever pull values forward — but not for two-way communication (a value passed to `.next(v)` can't be fed back into an already-finished run) or genuinely infinite/lazy generators, which still run to completion up front, gated only by the interpreter's pre-existing runaway-script timeout. Documented as a known ceiling in the code rather than silently pretending to be a full implementation.

8. **Computed property keys coerced through native `String()`, which has no idea how to render this engine's own object values.** `obj[expr]` and `{[expr]: ...}` both converted `expr`'s value with TypeScript's real `String()` — for this engine's own symbol objects (a plain data structure, not a real native `Symbol`), that produces the generic `Object.prototype.toString` fallback `"[object Object]"` for *every* symbol, so `obj[Symbol.iterator] = fn` and a hand-written custom iterable (`{[Symbol.iterator]: function(){...}}`) were both unreadable by anything that later looked the same property up correctly — including the new `for...of` Symbol.iterator support from root cause 6. Added a `toPropertyKey()` helper used at all 9 computed-key call sites in `interpreter.ts`: a symbol object gets a stable, per-symbol key derived from its unique internal id (so two different symbols never collide, unlike keying off the description, which two `Symbol('x')` calls could share); everything else goes through this engine's own `toString()` instead of native `String()`, fixing the same class of misrendering for any other of this engine's own object types used as a key.

9. **Several newer built-ins didn't exist:** `Array.prototype.toSorted`/`toReversed`/`with` (ES2023 non-mutating counterparts of `sort`/`reverse`/index-assignment), `Object.groupBy` (ES2024), `String.prototype.normalize`/`localeCompare`. Added all, using the real native TypeScript implementations underneath (`Array.prototype.sort`/`reverse`, `String.prototype.normalize`/`localeCompare`) rather than reimplementing them.

10. **Function parameter binding was a naive positional zip that only worked for plain identifier parameters — for every function in the engine, not just arrows (root cause 11 covers arrows' own, additional problem).** `createFunction`'s four call sites reduced every parameter to `(p as AST.Identifier).name` before the function was ever created, discarding the real AST entirely; a `RestElement`, `AssignmentPattern` (default value), `ArrayPattern`, or `ObjectPattern` parameter has no `.name` field, so this silently produced the parameter name `undefined` — meaning the *real* parameter name (`rest`, or whatever the default/destructured parameter was called) was simply never in scope in the function body at all. `function tag(strings, ...vals) { return vals.join(','); }` — a completely ordinary tagged-template-handler pattern — always saw `vals` as `undefined`. Fixed by preserving the real parameter AST nodes on `JSFunction` (a new optional `paramNodes` field, populated at all four `createFunction` call sites) and adding a `bindParams()` helper that, when `paramNodes` is present, binds each parameter through the interpreter's own pre-existing `destructPattern()` (already correct for `var`/`let`/`const` destructuring declarations, just never wired up for parameters) instead of the naive zip — used at all 7 places a function's parameters get bound (both `evalCall`'s and `callFunction`'s closure-invocation paths, the async-continuation resumption path, the class-constructor path, and the generator-body path from root cause 7).

11. **Arrow function parameters lost all destructuring/default/rest shape at parse time, on top of root cause 10 — `({a, b}) => a + b` returned `undefined` outright, not just a broken destructure.** Arrow-vs-parenthesized-expression is inherently ambiguous in JS grammar until the `=>` is actually seen, so this parser (like most) parses the parenthesized content as a *generic expression* first, then reinterprets it as a parameter list once `=>` follows (`parseArrowFunctionFromParams`). That reinterpretation step only ever extracted plain `Identifier` elements from the parsed expression, silently *dropping* anything else — an object/array literal, a default-value assignment, a spread — so `(a, {b, c = 5}) => ...` ended up with the single parameter `a` and no trace that a second parameter was ever written. Separately, `{b, c = 5}` and `` (...args) `` weren't even parseable as generic expressions at all: object-literal shorthand parsing had no path for `identifier = default` (only `identifier:` and bare `identifier`), and spread has no legal place in ordinary comma-expression grammar. Fixed with three changes: (a) `parseProperty()` now accepts `identifier = expr` shorthand, permissively, matching how real engines parse this speculatively; (b) a new `expressionToPattern()` converts an already-parsed `Identifier`/`AssignmentExpression`/`ArrayExpression`/`ObjectExpression`/`SpreadElement` tree into the matching `Identifier`/`AssignmentPattern`/`ArrayPattern`/`ObjectPattern`/`RestElement` pattern node, used by both `isValidArrowParams` (now correctly recognizing these shapes as valid) and `parseArrowFunctionFromParams` (now converting every element instead of silently keeping only identifiers); (c) `parseParenExpression` now builds its comma-separated item list by hand instead of delegating straight to the generic expression parser, so a leading or embedded `...` can be recognized and wrapped as a `SpreadElement` before it's reached as if it were an ordinary expression term. Combined with root cause 10's `paramNodes`/`bindParams`, arrow functions with any parameter shape now bind exactly like a regular function.

12. **`TextEncoder`/`TextDecoder` did not exist.** Wrapped the real native ones (same "reuse the real native implementation this engine's own TypeScript already runs in" pattern as `URL`), bridging `encode()`'s output through the sandboxed `Uint8Array` constructor (looked up lazily at call time, since typed array globals are registered later in `createGlobalEnv` than this code runs) so it returns a real, usable typed array rather than a bare array of byte values, and reading `decode()`'s input back off a wrapped typed array's real backing view.

## Notes
- Every fix in this document was found via the same standalone `HtmlParser`+`DomTree`+`runJS()` harness (no Electron/Playwright) established earlier in the day for the try/catch-escape investigation — a broad probe script exercising many unrelated APIs in one pass, then isolating whichever ones came back wrong into their own minimal repro. This stayed far faster than a real Electron relaunch per iteration even as the number of distinct bugs climbed into the double digits.
- Root causes 10 and 11 are the same class of bug at two different layers (interpreter-level parameter *binding*, parser-level parameter *shape capture*) and were found in that order specifically because fixing 10 alone wasn't enough to make `({a,b}) => a+b` work — the parser had already thrown away the fact that there even was a second parameter before the interpreter ever got a chance to bind it correctly. This mirrors the pattern from earlier in the session where fixing the try/catch escape bug did not, by itself, fix any of the specific API gaps it had been masking — each layer had to be fixed before the next one's bug became visible.
- `getPropertyValue`'s existing prototype-chain walk (added in an earlier, unrelated session) is what makes `Map`/`Set`'s `entries()`/`values()`/`next()` methods findable at all, since those live on `mapProto`/`setProto`, not on each instance directly; the new `for...of` rewrite deliberately routes through `this.getPropertyValue(obj, key)` rather than reading `obj.properties.get(key)` directly for exactly this reason — an early draft that read the instance's own properties map missed the prototype-chain methods entirely and needed a second pass to fix.
- Generators (root cause 7) are the one fix in this document with a real, documented ceiling rather than a full implementation — noted explicitly in the code (`runGeneratorBody`'s own doc comment) rather than left to be discovered as a surprise later: two-way `.next(value)` communication and genuinely infinite/lazy generators don't work correctly, only the "yield a sequence of values, consume them forward" pattern does. This was a deliberate scope decision given a tree-walking interpreter has no cheap way to add true suspend/resume without a much larger rewrite (a bytecode VM with resumable frames, or restructuring the entire evaluator around continuations) — explicitly out of scope for a same-day bug-hunting pass.
- All scratch investigation files (a rebuilt `scratch-run-js.mjs` harness and a `probe/` directory of ad-hoc repro scripts) were deleted before committing; the fixes worth permanent regression coverage were folded into a new `language-features` case in the existing `tests/e2e/js-dom-api-sweep.spec.ts` rather than a new file, matching this session's established pattern of merging related sweep work into one growing spec.
